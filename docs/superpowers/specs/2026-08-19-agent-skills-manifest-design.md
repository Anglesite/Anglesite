# Agent Skills manifest — design (#1579)

Slice 4 of the #1326 Agent Readiness ladder: publish `/.well-known/agent-skills/` so Cloudflare's
Agent Readiness scan's `agentSkills` check (part of its "Capabilities" category) passes for sites
that actually have visitor-facing capability to describe.

## Spec target

Cloudflare's [Agent Skills Discovery RFC](https://github.com/cloudflare/agent-skills-discovery-rfc)
(the mechanism `isitagentready.com`'s own scan checks for) defines:

- `/.well-known/agent-skills/index.json` — `{ "$schema": "<opaque schema URI>", "skills": [...] }`.
  Clients **MUST ignore unrecognized fields** — the extensibility rule this design leans on for its
  ownership marker (see below).
- Each `skills[]` entry: `name` (1–64 chars, lowercase alphanumeric + hyphens, no leading/trailing
  or doubled hyphen), `type` (`"skill-md"` here — no archive-type skills), `description` (≤1024
  chars), `url` (RFC 3986 reference, resolved against the index's own URL — a root-relative path
  like `/.well-known/agent-skills/<name>/SKILL.md` needs no `SITE_URL` to construct), `digest`
  (`sha256:<64 lowercase hex chars>` of the referenced file's raw bytes).
- Each `SKILL.md`: YAML frontmatter (`name`, `description`) then free-form Markdown body.
- Servers SHOULD serve `index.json` as `application/json` and `SKILL.md` as `text/markdown` (default
  static-asset MIME inference already covers both extensions; no Worker routing change needed, same
  as every other generated `.well-known` file in this template today).

This is the same discovery mechanism used for developer/coding-agent skills (e.g. Claude Code's own
skill directories) — but nothing in this template today publishes anything under
`.well-known/agent-skills/`, so there's no existing namespace to reconcile with. Out of scope.

## What's actually being described

Four visitor-facing tasks, each gated on whether the capability is *really* live for this build —
same honesty principle as the ladder ordering and every other generator in `edge-artifacts.ts`
(a `robots.txt`/`security.txt` this template writes only describes what's actually configured).

| Skill name | Enabled when | Points the agent at |
|---|---|---|
| `subscribe-feed` | always | `/rss.xml`, `/atom.xml`, `/feed.json` — all three are unconditional site routes today |
| `send-webmention` | `readConfig("WEBMENTION_RECEIVE_ENABLED") === "true"` | `POST /webmention` (form-encoded `source`+`target`) |
| `contact-site-owner` | `src/pages/contact.astro` exists | `/contact` |
| `book-a-time` | `src/pages/book.astro` exists | `/book` |

Two deliberate choices on the gating signals:

- **`WEBMENTION_RECEIVE_ENABLED` mirrors the existing gate** `BaseLayout.astro` already uses for
  `<link rel="webmention" href="/webmention">` — reusing the site's own established "is this truly
  on" signal rather than inventing a second one.
- **Contact/booking are gated on file existence, not `.site-config` provider values**
  (`CONTACT_PROVIDER`/`BOOKING_PROVIDER`). Those pages come from `integrations/pages/{contact,book}.astro`,
  copied into `src/pages/` by the app's contact/booking wizard skill. A provider value can exist in
  `.site-config` before that copy finishes (or after a page is later removed by hand), so checking for
  the page file itself is the only signal that guarantees the URL the skill advertises actually
  resolves. `.site-config` values still exist for the pages' own runtime behavior (which provider,
  what button text) — this manifest just doesn't use them as the *activation* signal.

No master on/off toggle: `subscribe-feed` is unconditional, so the manifest is never empty and
there's nothing meaningful for a toggle to suppress. No other generator in this family
(`security.txt`, `mta-sts.txt`, `atproto-did`) has an independent opt-out either — activation already
tracks the underlying feature's own config/on-disk state.

## Architecture

Mirrors `edge-artifacts.ts`'s existing plan/apply shape exactly (`planSecurityTxt`/`applySecurityTxtPlan`,
`planMTAStsPolicy`/`applyMTAStsPlan`, etc.) — pure decision functions, thin apply functions that touch
disk, wired into the same `main()`.

**New file: `Resources/Template/scripts/agent-skills.ts`**

- `AGENT_SKILLS: { name, description, active(ctx) => boolean, body(ctx) => string }[]` — one entry
  per row in the table above, `ctx` carrying `{ cwd, siteUrl }`. `body()` renders task URLs as
  `${siteUrl}${path}` when `SITE_URL` is configured (an off-site agent needs a full origin to act on
  the instructions), falling back to the bare root-relative path otherwise — the same optional-`siteUrl`
  handling `buildSecurityTxt`'s `Canonical` line already uses.
- `AGENT_SKILLS_MARKER` — an HTML-comment line (`<!-- Generated by Anglesite — do not edit; this
  file is regenerated from site config each build -->`) written as the first line of every generated
  `SKILL.md`'s body, after frontmatter. Detected as `isAgentSkillsDocOwned(content)`.
- Index ownership marker: an extra top-level `"generator": "anglesite"` field in `index.json`. Safe
  under the RFC's "clients MUST ignore unrecognized fields" rule — same idea as the literal first-line
  marker `security.txt` uses, adapted to JSON's syntax. Detected as `isAgentSkillsIndexOwned(content)`.
- `planAgentSkills(ctx, existing): { toWrite: {path, content}[], toDelete: string[] }` — pure. For
  each of the 4 known skills: active → included in `toWrite` (its `SKILL.md`) and in the index; not
  active but its `SKILL.md` exists and is marker-owned → its directory goes in `toDelete` (mirrors
  `planAtprotoDid`'s `delete-stale` case, scoped small since the skill catalog is a fixed set of 4,
  not an open-ended directory scan). `index.json` is always in `toWrite` (computed last, once the
  final active set and each written `SKILL.md`'s digest are known).
- `applyAgentSkillsPlan(publicDir, plan)` — carries out the plan: `mkdirSync`/`writeFileSync` per
  `toWrite` entry, `rmSync` per `toDelete` entry, `console.log` per action (existing convention).

**Wiring**

- `edge-artifacts.ts`'s `main()`: read `src/pages/contact.astro`/`book.astro` existence and
  `WEBMENTION_RECEIVE_ENABLED`, build `ctx`, call `planAgentSkills`/`applyAgentSkillsPlan` alongside
  the other `applyXPlan()` calls.
- `well-known.ts`'s `isGeneratedArtifact()`: add `isAgentSkillsIndexOwned(content) ||
  isAgentSkillsDocOwned(content)` to the existing `||` chain, so postbuild `verify` recognizes this
  generator's own output as claimed (same reason `security.txt`/`mta-sts.txt`/`atproto-did` are
  already in that chain).
- `Sources/AnglesiteCore/WellKnownInventory.swift`'s `GeneratedEndpoints`: new `Descriptor`s
  (`agentSkillsIndex`, `agentSkillsDoc`) plus marker constants mirroring `securityTxtMarker`/
  `mtaStsMarker`, wired into `matching(content:suffix:)` — `index.json` suffix + marker field,
  `agent-skills/<name>/SKILL.md` suffix pattern + marker line. `owner: "generator:agent-skills"` for
  both (one generator, unlike security.txt/mta-sts which are genuinely separate protocols).
- `Sources/AnglesiteCore/AgentReadinessReport.swift`: flip `"agentSkills"`'s `anglesiteProvides` to
  `true`.

## Testing

- `agent-skills.ts` under `npx tsx --test` (this template's convention — see
  `docs/superpowers/specs/...` test-convention notes and existing `edge-artifacts.test.ts`):
  - Each skill's `active()` against its gating input (on/off matrix).
  - `planAgentSkills` — full-activation and zero-optional-activation (only `subscribe-feed`) cases;
    digest correctness (`sha256:` + known hash of fixed content); stale-removal when a
    previously-active skill's gate turns off between builds.
  - `index.json` shape: `$schema`, `generator: "anglesite"`, one entry per active skill, valid
    `sha256:{64 hex}` digests, names satisfying the naming-rule regex.
  - `SKILL.md` shape: frontmatter `name`/`description` match the index entry; marker line present.
- `WellKnownInventoryTests.swift`: classification tests for both new descriptors (mirrors
  `securityTxtMarkerClassifiesAsGenerated`/`mtaStsMarkerClassifiesAsGenerated`), plus a
  `markersMatchTemplateSource`-style drift guard asserting the Swift marker literals still appear
  verbatim in `agent-skills.ts`.

## Out of scope

- An owner-facing toggle to suppress the manifest entirely (see "No master on/off toggle" above).
- Reconciling with a future developer/coding-agent skills feature sharing the same
  `.well-known/agent-skills/` namespace — no such feature exists in this template today.
- Any change to how static assets get their `Content-Type` (`.json`/`.md` MIME inference is already
  handled by the default static-asset serving every other generated `.well-known` file relies on).
- A site owner hand-authoring a custom skill under `public/.well-known/agent-skills/<name>/` — the
  whole subdirectory is gitignored (not tracked per-file like the other generated entries) and
  `index.json` only ever lists the four known catalog skills, so a hand-authored addition wouldn't
  survive a fresh clone or appear in the index.
